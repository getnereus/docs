    MCP as platform interface¶

    Thesis tested: the platform catalog (Backstage: Domain/System/Component/API/Resource, ownership, dependencies) serves as context for AI agents through MCP: the same catalog serves the portal (human) and MCP (agent). Result: confirmed by a primary source in upstream Backstage (catalog-backend registers catalog read actions that mcp-actions-backend exposes as MCP tools) and, as vendors, in Port, Spotify Portal and Red Hat Developer Hub.

    What MCP is (spec)¶

    • Literal definition: "Model Context Protocol (MCP) is an open protocol that enables seamless integration between LLM applications and external data sources and tools." — https://modelcontextprotocol.io/specification/latest
    • Architecture: "The protocol uses JSON-RPC 2.0 messages to establish communication between: Hosts: LLM applications that initiate connections; Clients: Connectors within the host application; Servers: Services that provide context and capabilities." — same URL.
    • Official analogy with LSP: "In a similar way, MCP standardizes how to integrate additional context and tools into the ecosystem of AI applications." — same URL. Useful for the talk: just as LSP decoupled the editor from the language, MCP decouples the agent from the system.
    • Version: "The current protocol version is 2026-07-28." Format YYYY-MM-DD, "to indicate the last date backwards incompatible changes were made." — https://modelcontextprotocol.io/specification/versioning
    • Revision 2026-07-28 declares the protocol stateless: "Stateless, self-contained requests" and "Per-request capability negotiation"; negotiation by handshake applies only to "2025-11-25 and earlier". — overview and versioning above.

    Server primitives: who controls each one¶

    • Literal list: "Resources: Context and data, for the user or the AI model to use"; "Prompts: Templated messages and workflows for users"; "Tools: Functions for the AI model to execute". From client to server: "Elicitation: Server-initiated requests for additional information from users". — https://modelcontextprotocol.io/specification/latest
    • Tools are "model-controlled, meaning that the language model can discover and invoke tools automatically based on its contextual understanding and the user's prompts." — https://modelcontextprotocol.io/specification/2026-07-28/server/tools
    • Resources are "application-driven, with host applications determining how to incorporate context based on their needs" and serve to "share data that provides context to language models, such as files, database schemas, or application-specific information." — https://modelcontextprotocol.io/specification/2026-07-28/server/resources
    • Prompts are "user-controlled, meaning they are exposed from servers to clients with the intention of the user being able to explicitly select them for use." — https://modelcontextprotocol.io/specification/2026-07-28/server/prompts
    • Optional extensions in the current revision: Tasks ("Asynchronous execution of long-running operations"), Skills over MCP and MCP Apps ("Interactive UI elements ... rendered inline within conversations"). — https://modelcontextprotocol.io/specification/latest
    • Reading for the presentation: the catalog fits naturally in resources (context, read) and the platform's actions in tools (execution). In Backstage, however, everything comes out as a tool (see below), including reading the catalog.

    Governance: Linux Foundation / Agentic AI Foundation¶

    • "Anthropic is donating MCP to the Agentic AI Foundation, a directed fund under the Linux Foundation." — official MCP blog, 2025-12-09: https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/
    • Technical governance unchanged: "The people making decisions about the protocol are still the maintainers who have been stewarding it, guided by community input through our SEP process." — same URL.
    • The AAIF was born with three founding projects: MCP (Anthropic), goose (Block) and AGENTS.md (OpenAI). — https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation

    Backstage: catalog exposed as MCP (upstream, not vendor)¶

    • Mechanism in two pieces. Actions Registry: "The Actions Registry Service is a core service designed to provide a distributed registry for actions that can be executed within Backstage backend plugins." Status (alpha). — https://backstage.io/docs/backend-system/core-services/actions-registry/
    • MCP Actions Backend: "The MCP Actions Backend exposes actions registered with the Actions Registry as MCP tools." Package @backstage/plugin-mcp-actions-backend; default Streamable HTTP endpoint http://localhost:7007/api/mcp-actions/v1; plugins exposed through backend.actions.pluginSources (e.g. 'catalog'). — https://backstage.io/docs/ai/mcp-actions/
    • Landed in v1.40.0 (tag of 2025-06-17): "A new mcp-actions backend plugin, which will surface these actions as tools as an MCP server. This can be used to expose plugin Actions with your favourite AI tools, such as Cursor, Claude or ChatGPT." With the warning: "it's currently highly experimental and could be subject to breaking changes in future releases." — https://backstage.io/docs/releases/v1.40.0/
    • Actions that catalog-backend itself registers (source code on master, checked on 2026-10-07; latest Backstage release v1.55.3, 2026-09-29): get-catalog-entity, query-catalog-entities, get-catalog-model-description, register-entity, unregister-entity, refresh-catalog-entity, validate-entity. — https://github.com/backstage/backstage/tree/master/plugins/catalog-backend/src/actions
    • get-catalog-entity: "This allows you to get a single entity from the software catalog. ... Each entity is identified by a unique entity reference, which is a string of the form "kind:namespace/name"." Attributes readOnly: true, destructive: false, idempotent: true.
    • query-catalog-entities documents ownership-relation queries for the LLM: "Querying relations - find all entities owned by a specific group: { query: { "relations.ownedby": "group:default/team-alpha" } }". It is direct proof of the thesis: the catalog's ownership and relations reach the agent as a tool filter.
    • get-catalog-model-description: comment in the code: "Lets users fetch a markdown formatted description of the catalog model. This is useful for informing LLMs how to properly work with it." Tool description: "Returns a markdown formatted description of the current catalog model, including all registered entity kinds, annotations, labels, tags, and relations."
    • Controls: destructive/readOnly/idempotent attributes per action, and visibilityPermission, which filters the action out of the listing and returns 404 on invocation for those without permission; it reuses the portal's permission framework. — https://backstage.io/docs/backend-system/core-services/actions-registry/
    • MCP auth in Backstage: static token ("temporary workaround"), CIMD (recommended, aligned with the spec) and DCR (deprecated). — https://backstage.io/docs/ai/mcp-actions/

    Other platform products with MCP (vendor)¶

    • Spotify Portal (vendor): "Portal exposes its plugin capabilities as MCP (Model Context Protocol) tools that any compatible AI agent can discover and use." Plugins in the diagram: Catalog, Soundcheck, Scaffolder. — https://backstage.spotify.com/docs/portal/core-features-and-plugins/mcp/overview
    • Red Hat Developer Hub (vendor, Backstage distro): "Starting in version 1.8, you can install plug-ins from the Extensions Marketplace that provide an MCP server in Developer Hub". Tools: software-catalog-mcp-tool and techdocs-mcp-tool. — https://developers.redhat.com/articles/2025/11/10/mcp-red-hat-developer-hub-chat-your-catalog
    • Port (vendor): "The Port Model Context Protocol (MCP) Server acts as a bridge, enabling Large Language Models (LLMs) - like those powering Claude, Cursor, or GitHub Copilot - to interact directly with your Port.io developer portal." — https://docs.port.io/agent-management/port-mcp-server/overview/
    • Humanitec (vendor): the MCP is about product knowledge, not about the customer's platform: the assistant "does not have access to any data within your Orchestrator organization". A useful counterexample: not every "platform MCP" exposes the platform's state. — https://humanitec.com/blog/feature-announcement-mcp-knowledge-server (the quoted sentence came from the former docs page, which now answers 404)
    • Upbound Crossplane (vendor): "MCP servers, packaged as Add-Ons...install on your control plane. They deliver tools that the language model can use." Intelligent Control Planes "bring LLM-driven logic into your control plane's reconcile loop." Note: in Upbound's docs "MCP" also means managed control plane. — https://docs.upbound.io/manuals/uxp/features/intelligent-control-planes
    • Argo CD (argoproj-labs project, Argo community, donated by Akuity): "An implementation of Model Context Protocol (MCP) server for Argo CD." Has an MCP_READ_ONLY mode that turns off create/update/delete/sync. — https://github.com/argoproj-labs/mcp-for-argocd

    Risks and auth (spec)¶

    • Tool Safety principle: "Tools represent arbitrary code execution and must be treated with appropriate caution." and "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server." and "Hosts must obtain explicit user consent before invoking any tool". The protocol admits the limit: "MCP itself cannot enforce these security principles at the protocol level". — https://modelcontextprotocol.io/specification/latest
    • Human in the loop: "For trust & safety and security, there SHOULD always be a human in the loop with the ability to deny tool invocations." Servers "MUST: Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs". — https://modelcontextprotocol.io/specification/2026-07-28/server/tools
    • Tool poisoning, prompt injection and rug pull (official tutorial, non-normative): "Tool names and descriptions are instructions your model reads. A server can hide directives in them that steer the agent — including how it uses other servers' tools — without the poisoned tool ever being invoked (often called tool poisoning, or tool shadowing when it targets another server's tools)." and "a server can quietly change them after you approved it (a rug pull)". Also: "Prompt injection in untrusted content can steer an honest server into the same overreach". And the principle: "no check proves what a server will do." — https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security
    • Auth in the spec: "Authorization is OPTIONAL for MCP implementations." When present, it is based on "OAuth 2.1 IETF DRAFT (draft-ietf-oauth-v2-1-13)" + RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207, CIMD. "A protected MCP server acts as an OAuth 2.1 resource server". "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728)." DCR "is deprecated" in favor of Client ID Metadata Documents. — https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization
    • Audience binding: "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" and "MCP servers MUST NOT accept or transit any other tokens." — same URL.
    • Security Best Practices lists: Confused Deputy, Token Passthrough ("explicitly forbidden"), SSRF, State Handle Hijacking, Local MCP Server Compromise, OAuth Authorization URL Validation, stdio in proxy, Mix-Up, Localhost Redirect URI Impersonation, CIMD Trust Policies, Scope Minimization ("Poor scope design increases token compromise impact, elevates user friction, and obscures audit trails."). The normative page does not cover prompt injection/tool poisoning; those are in the local server tutorial. — https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices

    Not verified¶

    • MCP adoption numbers in the first year (e.g. "97 million monthly SDK downloads", "10,000 active servers") appeared in a search summary attributed to the AAIF announcement; the literal sentence was not checked on the Linux Foundation/Anthropic page. Do not use on a slide without rereading.
    • AAIF supporting members beyond the three founders (Google, Microsoft, AWS, Cloudflare, Bloomberg): only via a search summary.
    • Current maturity status of mcp-actions-backend ("highly experimental" is from v1.40.0; the package is still 0.x, 0.2.3-next.1 in package.json on master). No GA declaration was found.
    • Spotify Portal: the MCP's beta/GA status is not stated on the page.
    • Red Hat Developer Hub: whether the MCP plugins are Tech/Developer Preview: the article does not say; Red Hat's product documentation was not read.
    • Port: the exact list of tools and the permission model ("runs with the signed-in user's permissions") came from a search summary; the page read does not have the literal text.
    • Kubernetes MCP: containers/kubernetes-mcp-server exists ("Model Context Protocol (MCP) server for Kubernetes and OpenShift"), but no official documentation from the Kubernetes project adopting an MCP server was found; do not cite it as "official Kubernetes".
    • Upstream Crossplane (not Upbound): no official MCP server documentation was found on crossplane.io.

    Use in the presentation¶

    • Candidate slide catalog-as-context (catalog: portal for humans, MCP for agents): the proof is upstream Backstage's query-catalog-entities filtering by relations.ownedby, plus get-catalog-model-description made explicitly "for informing LLMs". Message: one catalog, two consumers; the portal's permission framework (visibilityPermission) is the same one that filters the agent's tools.
    • Link with many-clients (CLI + MCP already cited through formae): Backstage's CLI (catalog module) and MCP consume the same Actions Registry actions: same surface, different clients.
    • Link with agent-identity (MCP auth): MCP server = OAuth 2.1 resource server, mandatory audience binding, token passthrough forbidden, CIMD in place of DCR; Backstage already follows this (CIMD recommended, DCR deprecated).
    • Risk note for the slide (a sentence in the notes, not on screen): a tool description is an instruction the model reads: tool poisoning/rug pull; that is why the exposed catalog should be read-only by default (readOnly: true) and destructive actions go through a human in the loop.
    • Optional counterexample: Humanitec exposes an MCP for documentation only: "having an MCP" does not imply exposing the platform's state.
